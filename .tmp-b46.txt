1: # SmartDesk AI · 企业内部服务台 Agent
2: 
3: **用自然语言问制度、查工单、建单、关单。Agent 要么给出带引用的答案，要么把写操作做成分级闸门——只读直通，可逆写要本人确认，不可逆/对外要主管审批，停下时状态写进 checkpoint，换个进程也能接着批。**
4: 
5: ![会话工作台：一次关单动作停在审批闸门](docs/screenshots/02-chat-approval.png)
6: 
7: 核心不是"把知识库接进模型"，而是把 **回答** 和 **动作** 分开：
8: 
9: - **回答**只依据检索到的制度，强制带 `[1][2]` 引用，找不到就说"知识库没有这条"并给下一步；
10: - **动作**按危险程度分级，风险不是静态配置：关单时勾了"通知提单人"，风险就从「可逆写」自动升到「不可逆写」；
11: - **谁批准**由权限算出来，不由对话里说了什么算：恢复时按恢复人的角色二次鉴权，发起人批自己的单会被标 `self_approved`。

189: ## 已知边界
190: 
191: - 没有登录/JWT：身份走请求头（`X-User-Id` / `X-Tenant-Id` / `X-Roles`），权限在 MCP server 侧校验；

193: - 单 Agent：单链路业务，拆多 Agent 只会多同步成本；
194: - 审批只做"关单并通知""发布知识"两类不可逆动作，未覆盖派单 / SLA / 流转；
195: - 参数抽取是规则不是模型：省一次 LLM 调用、防单号幻觉，抽不到的交给 `ask_missing_info` 反问；
196: - 审批完成后**发起人不会收到推送**：审批中心改的是 `approvals` 表和会话的 checkpoint，员工那页要再发一句话 / 刷新才看得到结果（真实系统这里要接消息通知）；
197: - 一条 thread 同时只能有一个挂起中的待办：挂起期间再发消息会返回 409，避免把 checkpoint 冲掉（前端已提示先处理卡片）。

201: - **kb server 启动会预热 import**（`backend/app/mcp/servers/kb_server.py` 的 `_warmup()`）：FastMCP 把同步工具放到 worker 线程执行，`pymilvus`/`numpy` 的 C 扩展在该线程里首次 import 会卡住不返回；提前在主线程 import 一次，代价是每个 kb 工具子进程多约 1 秒启动时间。

105: ## 3. 八个"为什么"（面试主战场）
106: 
107: 1. **为什么用 LangGraph 手写，不用 `create_agent`？**
108:    因为我要的是"**停下来等人**"：审批要跨进程、要能按新参数重算风险、要留痕。高层封装把工具调用交给模型自由决定，审批与审计就不可控了。
109: 
110: 2. **为什么 9 个节点这样切？**
111:    沿一条请求的真实阶段切：理解 → 取证 → 分叉（回答/规划）→ 三个闸门 → 执行 → 拼话。每个节点只干一件事，出问题能定位到节点。
112: 
113: 3. **为什么"制度和事实"要分两袋？**
114:    制度回答"规定是什么"（要引用），事实回答"这张单现在什么状态"（不要引用、不要编号）。混在一起会让模型把工具返回当制度引用，也会答非所问。
115: 
116: 4. **为什么风险必须由表决定，不能让模型判？**
117:    模型可以被话术骗。风险只能是 `RISK_BY_OP` + `compute_risk`（参数升级：关单 + 通知 = 不可逆），这样"危险等级"可测、可审计、可讲。
118: 
119: 5. **为什么"发起 ≠ 批准"？**
120:    员工该能提需求，但不能自己批自己。所以谁能发起是权限，能不能点通过看**恢复时**拿同一 `thread_id` 的那个人；有审批权的人自己批自己要标 `self_approved`。
121:    也正因为"谁在恢复"决定结果，`approvals` 表必须存 `thread_id`——否则审批中心看到一条待办，也不知道该 resume 哪条会话（它跟 checkpoint 是两个存储）。
122: 
123: 6. **为什么确认卡改完参数还要重算风险？**
124:    原本"关单"是可撤销，但勾了"通知提单人"就变成对外可见、不可撤回——不重算就会漏掉一道审批。所以 `confirm_action` 通过后重新 `compute_risk`，该升级就升级。
125: 
126: 7. **为什么只有 `execute_action` 能写库？**
127:    写操作集中在一个节点，才能保证"进到这里之前该批的都批了"，再补一道 `approval.approver` 兜底。别的节点只读。
128: 
129: 8. **为什么检索用 RRF 而不是加权分数？**
130:    稠密分数（余弦）和 BM25 分数不在一个量纲，归一化很脆；RRF 只用排名，稳、不用调参，取 `k=60` 让前几名权重接近、避免单路垄断。

157: ## 5. 四个"坑"（面试加分项）
158: 
159: 1. **恢复时节点会重跑**：`interrupt` 恢复不是"从下一行继续"，而是重放该节点。所以写审批留痕要幂等（`save_approval` 先查 pending）。
160: 2. **MCP 返回形状会变**：新版 adapters 返回 `[{"type":"text","text":...}]` 而不是 `ToolMessage`，所以要 `_text_of()` 兼容三种形状，否则建单报"无法解析的工具返回"。
161: 3. **Word 表格边框不可靠**：做简历/文档时 `tblBorders=none` 在 LibreOffice 里仍会画线——与项目无关，但说明"别相信渲染一致性"。
162: 4. **同步工具在 MCP worker 线程里首次 import 重依赖会卡死**：kb server 的工具调 `pymilvus`，FastMCP 把同步工具丢进 anyio worker 线程执行，那串 C 扩展在该线程里首次 import 实测 90s 不返回（栈停在 `numpy/_core/_multiarray_umath`；同样的 import 在主线程只要 1s）。表现是"调 `search_kb` 没反应、也不报错"。
163:    定位方法：`faulthandler.dump_traceback_later(15, repeat=True)` 打服务端栈，再用"进程内直调 handler（通）/ 普通线程 import（通）/ MCP stdio 调（挂）"三组对照把范围压到传输层。
164:    修法：`kb_server.py` 在 `__main__` 里 `_warmup()`，把 import 提前到主线程（只 import 不连库，`get_client()` 仍是懒连接），代价是子进程启动多约 1 秒。
