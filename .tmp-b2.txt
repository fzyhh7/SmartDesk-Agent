1: # SmartDesk AI · 企业内部服务台 Agent
2: 
3: 用自然语言提问或提需求，Agent 要么给出**带引用的答案**，要么生成**待确认的工单**，要么停在**人工审批**等有权限的人点头。

只要你是普通员工（`employee`），无论你在知识问答里提别人的单号，还是在 `query_ticket` 里查别人的单号，MCP Server 都会直接返回 `forbidden（你没有权限操作工单...）`，连工单标题都不会吐出来一个字。

#### 2. 为什么不能在 `classify` 节点赋权限值、或者在 `gather_evidence` 之前加鉴权节点？
试想一下這個场景：
- 员工 A（`user_id="u-1001"`, `role="employee"`）说：**“把工单 `TK-20261031-0001` 关掉。”**
- 请问：在刚走完 `classify_request` 的时候，你能判断员工 A 有没有权限关掉 `TK-20261031-0001` 吗？
- **判断不了！** 因为普通员工**可以关自己提的单，但不能关别人提的单**。在没去数据库查出 `TK-20261031-0001` 的提单人（`reporter`）是谁之前，任何节点都不知道这张单是不是员工 A 自己的！
- 这在安全领域叫 **RBAC（基于角色的权限，如 `publish_kb_article` 只要看是不是 `kb_owner`）** 与 **ABAC / 对象级权限（基于属性的权限，必须先查出工单是谁的，才能判断能不能改/关/查）** 的区别。
- 所以，鉴权**必须在 `gather_evidence`（查出工单归属）之后**才能做！而 `gather_evidence` 的下一个动作节点就是 `plan_action`——这就是为什么作者把 `not_allowed()` 放在了 `plan_action` 里，而不是放在 `classify` 里。

#### 3. 为什么不把权限放进 `State`，而要放进 `Runtime[UserContext]` + MCP Server？
这也是 [state.py:29–46](<backend/app/agents/state.py#L29-L46>) 特意设计的核心亮点（面试必考）：
1. **如果把权限属性放在 `State` 里**：
   - `State` 是会被序列化存进 PostgreSQL Checkpointer 的。
   - 当员工发起一个“发布知识库”请求，图停在 `approve_action`（写进了 `State`）。如果权限存在 `State` 里，那恢复运行的时候，图读到的还是当年发起人的旧权限；或者如果在节点里随便改 `State` 的权限字段，很容易在跨进程 Resume 时出现权限串号。
   - 放进只读的 `Runtime[UserContext]`（`frozen=True`），每次请求进来都从当前 HTTP 请求头实时注入，**永远不会进 Checkpoint 落盘，也不会被模型篡改**。
2. **为什么有了前置鉴权（`not_allowed`），MCP Server 里还要再鉴权一次？**
   - 前置的 `not_allowed` 是为了**用户体验（Fail-Fast）**：员工没权限时，别让人家填半天确认卡、排半天审批队，最后执行时才报错，而是在 `plan_action` 就直接礼貌劝退。
   - 后置的 MCP Server `guard.py` 是为了**安全底线（零信任）**：因为 MCP Server 是一个独立的服务，以后可能接别的 Agent，不能指望外面的 Agent 节点一定写了 `not_allowed`。

21:   let event = 'message'

## 1. 管理员不批，会不会卡在对话框？

**不会卡住连接，但有 3 个比“卡住”更实际的问题。**

先看不会卡的原因：

- 后端 [streaming.py:153–166](<backend/app/api/streaming.py#L153-L166>) 在 `graph.stream()` 结束后检查 `snapshot.interrupts`，若有，就发一个 `event: interrupt`，再 `return`，**SSE 流即关闭，HTTP 请求正常结束**；
- 前端 [ChatView.vue:132–146](<frontend/src/views/ChatView.vue#L132-L146>) 的 `consume()` 在 `finally` 里把 `running.value = false`，输入框恢复可用，只多出一张 `InterruptCard` 卡片。

所以员工侧体验是“挂起等审批”，而不是“转圈卡死”。管理员下一分钟来、明天来都可以，`thread_id` 一直有效。

**但下面几个才是真问题：**

**(a) 审批中心只能看，不能点通过。** 你打开 [ApprovalView.vue](<frontend/src/views/ApprovalView.vue>) 会发现整页只有表格和“刷新”按钮，**一个“通过/驳回”按钮都没有**。主管登录后在 page 上只能干瞪眼看到一条 `pending`。

**(b) 更致命的是，Web 端管理员拿不到别人的 `thread_id`。** 想在 Web 上批，前端必须调 `POST /runs/{thread_id}/resume`（[sse.ts:85–91](<frontend/src/api/sse.ts#L85-L91>)）。但 [ChatView.vue:38–40](<frontend/src/views/ChatView.vue#L38-L40>) 的 `threadId` 是本地随机生成的 `web-20261106...`，**页面上没有任何地方能输入或获取别人的 thread_id**。所以主管换一个浏览器、换一个身份进来，根本没法让 `threadId.value` 变成员工那条 thread —— **Web 端的跨角色审批实际是断的**。

目前真正能跑通“跨进程审批”的只有 CLI（[run_graph.py](<scripts/run_graph.py>)）：
```powershell
.venv\Scripts\python.exe -m scripts.run_graph resume --thread t3 --role approver --user u-9001 --approve
```

**(c) 没有任何超时/通知机制。** [settings.py](<backend/app/agents/settings.py>) 里有个 `approval_timeout_min = 1440`，但注释写着“MVP 不做超时轮询”，**没有任何代码引用它**。所以一旦管理员永远不批，那条 `pending` 就在 SQLite 里永远躺着，员工侧永远显示“等待中”，也不会有人被提醒。

**(d) 还有个隐蔽坑**：如果员工在挂起期间又在**同一个会话**里发了新消息，[routes.py:53](<backend/app/api/routes.py#L53>) 会重新 `initial_state` 并 `invoke`，直接覆盖这条 thread 的 checkpoint，原来的 interrupt 就丢了。之后主管再 resume，[routes.py:85–86](<backend/app/api/routes.py#L85-L86>) 会返回 `409 这个会话没有停在闸门上`。

## 2. `_call_tool` 里的 `server` 是冗余吗？——不是，你记反了

`action` 里**是有 `server` 的**。看 [plan_action.py:253–261](<backend/app/agents/nodes/plan_action.py#L253-L261>)：

```python
action_out = {
    **action,
    "server": server,   # ← 这里写进去了

```

作者那句注释“server 由 op 推导，不交给模型判断”的意思是：**不让大模型填 `server`**（[classify.py](<backend/app/agents/nodes/classify.py>) 的 `Classification` 里确实没有 server 字段），而是 `plan_action` 按 `op` 算出来（`publish_kb_article → kb`，其余 `→ ticket`），再写进 `action`。

server = action.get("server") or ("kb" if op == "publish_kb_article" else "ticket")

这是防**老 checkpoint**（升级前存的 State 里没有 `server` 字段）从 PG 里被恢复出来时炸掉。这属于**版本兼容**，是加分项而非冗余。

## 3. 闲聊固定话术 —— 这是真缺陷，而且你判断对了

看 [respond.py:20–24](<backend/app/agents/nodes/respond.py#L20-L24>)：

```python
def _chat_reply(state: TicketState) -> str:
    return "你好，我是企业服务台助手。你可以直接问我制度流程（例如「发票怎么开」「年假多少天」），也可以让我办事…"
```

注意这个函数**连 `state` 参数都没用**，返回的是硬编码字符串。

链路是这样的：[classify.py:100–101](<backend/app/agents/nodes/classify.py#L100-L101>) 判出 `intent == "chat"` → [graph.py](<backend/app/agents/graph.py>) 的 `route_after_classify` 直接把 `chat` 送进 `compose_reply`（不检索、不调模型）→ 命中固定问候语。

所以你说得完全对：
- 用户说“帮我讲个笑话” → `chat` → 回“你好，我是企业服务台助手…” ❌
- 用户说“你是谁 / 你能做什么 / 谢谢” → 固定话术还算能糊过去 ✅
- 用户说“今天几号” → 答非所问 ❌

**根因**：`chat` 分支为了省一次 LLM 调用（快、省钱）走了纯模板，但分类器的 `chat` 语义是“寒暄/感谢/与业务无关”，这两个范围不重合。

**修法有两个层次：**
- 轻量：在 `_chat_reply` 里用 `state["query"]` 做关键词匹配，问候/感谢/自我介绍走模板，其他 chat 兜底说“我只负责制度问答和工单，你这个我帮不上”。
- 正确：`chat` 分支也调一次 LLM（用很短的 prompt + 低 token），成本几乎可忽略，但体验正常。代价是多 1～2 秒。

## 4. 知识型回答会不会走 `respond`（`compose_reply`）？—— 会走，但不改写

[graph.py:107](<backend/app/agents/graph.py#L107>) 有明确的边：

```python
builder.add_edge("answer_with_citations", "compose_reply")
```

再看 [respond.py:112–121](<backend/app/agents/nodes/respond.py#L112-L121>)：

```python
def compose_reply(state):
    intent = state.get("intent") or "knowledge"
    reply = state.get("reply")
    if intent == "chat":
        reply = _chat_reply(state)
    elif intent == "action":
        reply = _action_reply(state)
    elif not reply:                      # ← knowledge 分支
        reply = "我没能生成回答，请换个说法再问一次。"
    return {"reply": reply}
```

`knowledge` 分支只有 `elif not reply:` 一条兜底。而 `answer_with_citations` 在 [answer.py:89–93](<backend/app/agents/nodes/answer.py#L89-L93>) 已经把 `reply` 写进 State 了，所以 `not reply` 为 `False`，`compose_reply` **原样透传**，不改一个字。

**为什么还要多走这一跳？** 因为作者想让**所有链路的出口统一**：不管知识问答还是动作执行，最后都经过 `compose_reply` 落到 `reply` 字段，这样 [streaming.py:95–109](<backend/app/api/streaming.py#L95-L109>) 的 `done` 事件只需要读一个 `reply`，前端也只认一个字段，不用为“从 answer 节点结束时谁来填 reply”写第二套逻辑。代价是多一个几乎零耗时的节点。
